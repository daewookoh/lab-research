## 1. 목적

`market_price.json`(D005)의 `search_index` 는 "관측일 기준 검색 트렌드 지수(0~100, 네이버 데이터랩식 상대 지수). D017 소스 확정 전까지 자리만 둔다" 로 비워 두었고, Re-Flow Score v0 시장수요 항목(D006 §3.1)은 이 값이 결측이면 가중치 0.2 를 브랜드·시즌에 재배분한다 — 즉 지금 v0 의 수요 항목은 사전값(브랜드 등급·시즌 표)만으로 결정된다(D012 고찰). D016 에서 판매량(`sold_count_30d`)을 주는 시세 소스가 0개로 확인됐으므로, 검색 트렌드는 **외부에서 얻을 수 있는 유일한 수요 신호**다. 오늘은 (1) 소스 후보와 약관, (2) 각 API 의 정확한 제약(호출당 키워드 수·기간·단위), (3) "상대지수" 를 상품·일자별 레코드로 쓸 수 있게 만드는 방법, (4) 소분류 30개를 어떤 키워드로 물을지를 정한다.

## 4. API 명세에서 확인한 것 (네이버 API HUB 데이터랩)

### 4.1 검색어 트렌드 `/search-trend/v1/search`
- 요청: `startDate`(≥ 2016-01-01)·`endDate`·`timeUnit`(`date|week|month`)·`keywordGroups[≤5]{groupName, keywords[≤20]}` 필수, `device`(pc|mo)·`gender`(m|f)·`ages`("1"~"11": 0~12세 … 60세 이상) 선택. 인증 `X-NCP-APIGW-API-KEY-ID` / `X-NCP-APIGW-API-KEY`. 날짜 범위 상한·일 단위 최대 기간은 문서에 없다.
- 응답: `results[]{title, keywords, data[]{period, ratio}}`. **`ratio` = "구간별 검색량의 상대적 비율 - 구간별 결과에서 가장 큰 값을 100으로 설정한 상댓값".**
- 문서가 "가장 큰 값" 이 **요청 전체** 기준인지 **그룹별** 기준인지 적지 않는다. 문서 예시 응답은 한 그룹만 100 이고 다른 그룹은 최대 29.7 이라 요청 전체 기준으로 읽히지만, 예시 하나로 단정할 수 없다. 이 한 가지가 설계를 가른다(§5).
- 한도: 개요 페이지의 429 설명이 "하루 허용량 초과" 라고만 한다. D016 가이드 기준 데이터랩 월 50,000건(오늘 재확인 실패). 요금 페이지 미열람.

### 4.2 쇼핑인사이트 `/shopping/v1/categories`, `/shopping/v1/category/keywords`
- 검색이 아니라 **네이버쇼핑 안의 클릭** 상대지수라 구매 의도에 더 가깝고 2017-08-01 부터 있다. 분야별은 category 3쌍, 키워드별은 category 1개 + keyword 5쌍이며 쌍당 검색어가 1개뿐이라 동의어를 묶을 수 없다.
- 단위가 네이버쇼핑 카테고리(`cat_id`)인데 코드표 API 가 없고 "네이버쇼핑에서 카테고리 선택 시 URL 의 cat_id" 로만 안내한다. 소분류 30개 ↔ cat_id 대응표는 사람이 화면에서 받아 적어야 한다 — `trend_keywords.yaml` 의 `naver_shop_cat_id` 가 전부 null 인 이유.
- 키워드별 예시 응답에 날짜가 빠진 구간이 있다(2023-11-04 없음). 파서는 빠진 구간을 0 으로 채우지 않는다.

### 4.3 Google Trends API (alpha)
- 웹의 "요청마다 0~100" 과 달리 **요청 간 일관된 척도**를 준다고 공식 블로그가 밝혔다(요약 기준). 이것이 네이버에 없는 장점이지만 알파 테스터 소수에게만 열려 있고 한국 검색 점유율이 낮아 보조 소스. 신청은 무료.

## 5. 상대지수를 레코드로 쓰는 방법 — 앵커 정규화 (`src/collect/trend_naver.py`)

- 문제: `ratio` 는 요청 안의 최대값이 100 인 상대값이라 호출이 다르면 비교가 안 된다. 소분류 30개는 호출 5그룹 제한 때문에 최소 6 호출에 걸치고, 시간이 지나 다시 부르면 척도가 또 바뀐다.
- 방법(요청 전체 기준 정규화일 때): **모든 호출에 같은 앵커 그룹**(`ANCHOR`: 생수)을 넣고 각 구간의 값을 앵커의 같은 구간 값으로 나눠 "앵커 대비 배수" 로 바꾼다(`normalize_by_anchor`, mode=period). 앵커의 시간 변동을 제거하므로 소분류 간·시점 간 비교가 가능하다. 앵커 평균으로 나누는 mode=mean 은 키워드 자체의 추세를 보존한다. 두 가지를 다 둔 이유는 어느 쪽이 판매기간과 더 상관되는지 실데이터로 봐야 하기 때문.
- `to_search_index`: 앵커 대비 배수 → 0~100 정수(앵커와 같음 = 50, 2배 이상 = 100, 선형). **가정**이며 D018 에서 분포를 보고 재조정.
- **그룹별 정규화라면 앵커 정규화는 무의미**하고 키워드 간 비교가 원천적으로 불가능하다(각 키워드 안의 시간 추세만 쓸 수 있음). `detect_normalization` 이 응답에서 판별한다(모든 그룹 최대 100 → per_group, 정확히 한 그룹만 100 → per_request). **샘플 호출 1건이면 결론이 나는 문제**라 D017b 의 첫 확인 항목으로 둔다.
- 앵커 "생수" 는 (1) 어느 소분류에도 없고 (2) 시즌성이 약하며 (3) 품목 키워드와 검색량 자릿수가 비슷할 것이라는 가정으로 골랐다. 앵커가 너무 크면 품목 ratio 가 1 미만 소수로 몰려 정밀도가 떨어지고(ratio 는 소수 5자리), 너무 작으면 품목이 100 에 걸린다. 샘플 호출 후 교체 가능.
- 호출 계획(`trend_naver_dryrun.txt`): 30 소분류 × 키워드 150개 → 앵커 1 + 소분류 4 = 호출당 5그룹, **8 호출/회차**. 월 1회 갱신 8건, 주 1회 32~40건 — 월 50,000 한도가 맞다면 0.1% 미만.
- 문서 예시 응답으로 파서·정규화 점검: 행 8개, 판별 per_request, 영어 그룹의 "한글" 대비 배수 0.30~0.38 → search_index 15~19. 숫자 자체는 의미 없고 경로가 끝까지 돈다는 확인.

## 6. 키워드 매핑 (`data/collect/trend_keywords.yaml`)

소분류 30개 × 키워드 5개 = 150개. `categories.yaml` 의 `examples` 에서 수량·규격("24입", "1L", "10족")을 떼고, 성별이 섞이는 의류는 "남자 티셔츠"·"여성 패딩" 처럼 구분어를 붙였으며, 물티슈처럼 두 소분류에 걸치는 어휘는 "유아 물티슈" 로 갈랐다(검증기: 소분류 간 키워드 중복 0, 누락 0, 앵커 포함 0). 키워드 선정은 examples 어휘 기준의 **가정**이고, 실데이터·과제2 입력에서 실제 품목명이 오면 다시 뽑는다. 쇼핑인사이트 `cat_id` 는 0/30.

## 7. 결론·권고

1. `search_index` 의 1순위 소스는 **네이버 API HUB 검색어 트렌드**다(키워드 단위·일간·2016년부터·호출 8건/회차). 그러나 clear 소스가 0개이고 1순위도 시세(D016)와 같은 약관 7.3③ 쟁점 아래 있다. **D016 질문 1 의 서면 확인에 "데이터랩 검색어 트렌드·쇼핑인사이트 ratio 를 상품·일자별 지수로 저장" 용도를 함께 넣어야 한다.** 네이버가 저장을 허용하지 않으면 데이터랩 웹 수기 다운로드(연구용 소량) 또는 Google Trends alpha 가 대안이고, 둘 다 안 되면 `search_index` 는 실데이터에서도 결측으로 남는다.
2. D017b(샘플 호출)는 키가 오는 즉시 **8 호출 1회**로 (a) 정규화 기준(요청 전체/그룹별) 판별, (b) 앵커 "생수" 의 자릿수 적합성, (c) 하루 한도 숫자(429 발생 여부)를 확인한다. 응답은 약관 확인 전까지 저장소에 넣지 않고 요약만 남긴다(코드가 그렇게 되어 있음).
3. 쇼핑인사이트는 cat_id 대응표(사람 작업 30건)가 선행이다. 분야별 트렌드는 소분류 단위 시즌 지수(D027)의 후보이므로 cat_id 는 D027 전까지 받으면 된다.
4. 검색광고 키워드도구는 유일한 절대치 소스다. 회사가 검색광고 계정을 갖고 있다면 앵커의 월간 검색수로 상대지수를 절대 검색수로 바꿀 수 있어 소분류 간 수요 크기 비교가 된다. 계정 보유 여부와 광고 외 용도 허용 여부를 질문.
5. 합성 v2 의 `search_index` 는 `uniform(0,100)` 노이즈(`src/data/synth.py:379`)라 수요 신호로서 아무 정보가 없다. 트렌드 소스가 확정되면 v2.1(D034)에서 시즌 상태·소분류와 연동된 지수로 바꿔야 D021 이후 모델이 이 피처를 평가할 수 있다 — D034 설명에 추가.
6. 크롤링(Google 비공식·오픈마켓 인기검색어)은 후보에서 제외. 3자 키워드 도구는 수기 참고용.

## 8. D017b·D018·D027·D034 에 넘기는 것

- D017b `[blocked]`: API HUB 키 + 서면 확인(D016 질문 1 확장). 확인 항목 §7-2.
- D018: 트렌드 수집은 시세와 같은 파이프라인에 "월 1회(또는 주 1회) 8 호출 → 앵커 정규화 → search_index" 단계로 넣는다. 저장 형식은 `market_price` 레코드의 `search_index` 가 아니라 **소분류·일자 단위 별도 테이블**이 맞다(시세 레코드는 상품×소스×관측일이고 트렌드는 소분류×일이라 조인 키가 다름) — D018 에서 `trend_index.json` 스키마 제안.
