## 4. 고찰
- 결론은 D016 과 같은 모양이다 — **clear 소스가 0개**. 검색 트렌드는 D016 에서 판매량 소스가 없다고 확인된 뒤 남은 유일한 외부 수요 신호인데, 그 1순위(네이버 데이터랩)도 시세와 같은 약관 7.3③ 아래 있다. 트렌드 문서 자체엔 저장·용도 조항이 없고 일반 약관이 적용되므로, D016 질문 1 의 서면 확인에 데이터랩 용도를 같이 넣는 것이 가장 싸다(문의 1건으로 두 소스가 풀린다). 거꾸로 네이버가 저장을 불허하면 시세와 트렌드가 한꺼번에 막히고, 그때 `search_index` 와 `price_*` 가 실데이터에서도 결측이 되어 v0 수요·가격 항목은 사전값과 수기 입력에만 기대게 된다.
- 기술적으로 가장 중요한 미확인은 **ratio 의 정규화 기준**이다. 요청 전체 기준이면 앵커 하나로 호출 간·시점 간 비교가 되지만, 그룹별 기준이면 키워드 간 비교가 원천적으로 불가능하고 각 키워드의 시간 추세만 남는다. 문서는 침묵하고 예시 응답 하나만 요청 전체 쪽을 가리킨다. 샘플 호출 1건이면 끝나는 문제라 D017b 의 첫 확인 항목으로 못 박았고, 판별 코드를 미리 넣어 키가 오면 바로 결론이 나게 했다.
- 상대지수를 레코드로 쓰려면 앵커가 필요한데, 앵커 선택이 곧 척도다. 앵커가 품목보다 훨씬 크면 품목 값이 소수점 아래로 몰리고(ratio 소수 5자리라 정밀도는 남지만 `to_search_index` 의 0~100 정수 변환에서 뭉개진다), 작으면 품목이 100 에 걸린다. "생수" 는 자릿수가 비슷할 것이라는 가정이며 샘플 호출에서 앵커 ratio 가 5~50 범위에 오는지로 판단하면 된다.
- 쇼핑인사이트가 검색보다 구매 의도에 가까워 매력적이지만 `cat_id` 코드표 API 가 없다는 점이 걸림돌이다 — 30개 소분류 대응표를 사람이 화면에서 받아 적어야 하고, 네이버쇼핑 카테고리가 바뀌면 깨진다. 키워드별 API 는 쌍당 검색어 1개라 동의어 묶기가 안 돼 범용 지수보다 특정 품목명(M7 이후) 용도다.
- 합성 v2 의 `search_index` 가 균등 노이즈라는 것을 오늘 확인했다. 지금 상태로는 D021 이후 모델이 이 피처를 넣어도 아무 것도 못 배우므로, 피처 중요도(D023)에서 "search_index 중요도 0" 이 나와도 그것은 소스 문제가 아니라 합성 설계 때문이다 — D034 설명에 교체 항목을 넣었다.
- 한계: 1차 확인 4/10. 데이터랩 월 한도(50,000)는 D016 기억값이고 오늘 재확인에 실패했다. Google Trends 블로그는 본문을 모델 요약으로만 읽었다. 검색광고 키워드도구는 이슈 2건만 읽어 필드·한도가 전부 기억 기준이다. 키워드 150개는 examples 어휘 기준이라 실제 품목명과 다를 수 있다.
